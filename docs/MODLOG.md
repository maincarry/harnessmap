## Standing rules distilled from the above

- The user controls the flow tangibly; the map is the product, chat is the interface.
- Automated map, no manual restructuring (M23) — the filer suggests (M24), never acts.
- Suggest-then-confirm for anything agent-initiated that re-aims the user (M15, M19, M24).
- Everything is a node (M29); statuses/types are open vocabulary, not schema.
- What the agent sees, the user can see (M20, M21's visible-omission rule).
- Machine-maintained memories are read-only to the user (M43); user edits touch only title/description/category.
- The light is the law (M47): it bounds the chat agent's background and the map agent's writes; reading may expand on demand, writing never; prompts guide, server guards enforce.
- No topic dignity threshold (M50): whatever the user deliberates is map material; only dialogue mechanics produce nothing.
- New-topic guarantee (M61): a topic absent from the map always leaves at least one node, however transient; mass same-status flips are mechanically capped.

## M71 — Precomputed dot proposals, cost-throttled (Jacob, 2026-08-17)
"Precompute proposals is exactly the right move, but it should happen not too often, so we do not run into trouble" — clarified: COST trouble. Design is cost-minimal: when a dot is filed (and at boot), a background sweep computes its proposal ONCE — ever — after a 25s settle debounce, serially (one per sweep), and never while the filer queue is busy. Cached on the suggestion row (`proposal` + `proposal_hash` = subtree updatedAt-hash). Click serves the cache instantly when the hash still matches (audit `proposal_cache_hit`); stale or feedback-carrying requests always compute live — the background NEVER recomputes. Net cost per dot ≈ one extra call, usually haiku via the adaptive tier. Bench: cached preview 16ms; touched child → live fallback.

## M72 — Tidy reads only the local neighborhood; whole-map read is tidy-map's job (Jacob, 2026-08-17)

Jacob: "we need some serious better integration of the preference" → the proposal, docs/PREFERENCES-DESIGN.md (page: the "Preferences as Map Nodes" artifact).
THE PROPOSAL, in one paragraph: preferences become NODES in a system chapter "preferences" (created like "to sort", never tidied, moved or removed by agents) and — the one new law — served whatever the light, because they are law, not content. They inherit what nodes have: a statement in the user's words, a status (live / superseded / parked), children for reasons and exceptions, and a timeline (a new rule on the same subject updates the old, which stays as a version). SCOPE IS PLACEMENT (Jacob's correction the same night: a scope table "seems unnecessary when preference becomes complex"): a rule in the top-level chapter is global, a rule placed under a chapter governs that subtree, one under a node governs that node — per-node rules come free; beside the node only an optional role and a mechanical guard form remain. Delivery is composed per call — the rules on the path from the touched node to the top, nearest first, plus the global chapter, about twelve by id — instead of the blob. Capture has three doors, all propose→approve: the editor, the map-chat, and the filer recognising "from now on / always / never" in any round. Every agent answers with the ids it applied and the ones it could not follow; the brain names a live rule never applied. Rules with a checkable form become code guards that REFUSE, like the budget guard. The brain's hidden taste becomes proposed preferences. Cost: no extra model calls. Four stages, about two working nights; Test 1 gains an adherence class.
