Harnessmap · Design v2

The map that writes itself

The user controls the flow tangibly — by understanding and prioritizing the goals of the conversation in the way they want.

Endorsed design · Jacob (07-17→07-19) + Mark's rulings (08-12) · v1 archived at docs/archive/DESIGN-v1.md · working docs in docs/ontology/

§ 1Thesis

Working with an AI today means one long chat: it fills with junk, side-topics pollute the main work, nothing is findable, and after a week away you re-read everything to remember where you were. The deep cause: chat products organize your thinking by time, and time is the wrong index for work.

Harnessmap replaces the long chat with a map of the work itself — what you're trying to do, what's decided, what's open, what's parked. You still converse with the AI; the chats become short working sessions, and the map is the lasting record.

The promise in three verbs: see everything that matters at a glance, point at any piece of it in plain speech, change it directly — and the system keeps everything consistent with your change.

The analogy that compresses it: a chat harness makes you work inside the commit log; harnessmap moves you into the codebase, with the log kept underneath for provenance.

§ 2The two layers

Everything lives on one of two layers, connected by exactly one bridge.

History layer (events)Goal layer (meaning)
turnitem
chatmap alteration set
a node's chat historya node's revision history
the logthe map
ordering: happened-beforeordering: frames / summarizes
immutable · total · singulareditable · partial · plural
attention by recencyattention by focus + lit set
  • The log is append-only, never edited. Every turn of every chat is kept forever, reachable by recall. Nothing done on the map can lose history.
  • The map is the editable structure of meaning — what users navigate, point at, rearrange. Many valid maps could describe one history; the user's map is theirs.
  • The bridge is the per-round translation loop (§4) — the ONLY mechanism turning history into map content. Map ops never touch the log; chat ops never directly edit the map. A feature ambiguous about its layer is a design smell.

A chat is temporal scaffolding: people and models think by conversing in time. Once translated, the chat archives to the log; what remains on the map is the meaning it produced.

§ 3Ontology: containers & items

The carving principle: a unit is whatever the user can point at and operate on in speech — "drop objection 1 to argument 2, that's bullshit." Location + separable identity + pointability. The user's referential habits ARE the ontology; the system only suggests.

Containers — locations that give addresses, from the deliverable's part-whole spine (essay → section; trip → leg). With no deliverable, the chat itself is the default container; items live homeless and structure crystallizes later (§6). Status: live | provisional | cut.

Items — the deliberation atoms:

item = (id, type, content, status, author, home container, role-links, provenance)

Seven types, domain-independent (validated on essay / travel / free-exploration transcripts):

TypeLifecycle
claim (incl. ideas)floated → proposed → accepted / rejected
questionopen → answered / mooted
optionlive → chosen / dropped
decisionproposed → decided / reversed
constraintactive / hard → relaxed / lifted
evidencenoted → cited / retracted
tasktodo → doing → done / dropped

Overlays: parked, dropped-as-noise. Role-links (typed, cross-container): supports · objection-to · replies-to · answers · motivated-by · satisfies · blocks · chooses.

  • "Goal" is not a primitive. A goal-node = a container + its live items — a view, not a stored kind.
  • Author matters: agent-created items enter floated and are promoted only by user engagement; containers require outright ratification. The agent cannot colonize the map.
  • Lazy granularity: items are as fine as pointing has needed. Pointing inside one triggers a split proposal.
  • Provenance everywhere: item ← round summary ← raw turns is the audit chain.
  • Dropped ≠ deleted: dropped items revive by pointing, history intact.

§ 4The bridge: per-round translation

Translation is per-round, never an end-of-chat batch — that is what connects the history layer to the goal layer continuously.

Per round (each message, agent turns included):
  input:  M (current map), buffer (exchange scratch), R (new message)
  1. S ← summarize(R), phrased in M's existing vocabulary
  2. classify: content-level → map alterations
               process-level → exchange buffer only
               map-level     → re-carve proposal (gated; deferred)
  3. alterations: update node | new connected subnode | new detached node
  4. apply; advance localization pointer + buffer
  • Map-conditioned summarization is the identity system — "the claim about authorship" resolves to thesis for free; project language stops drifting.
  • Eager creation: introduced topics become nodes at introduction (⚠ tentative, author-marked), pruned later — so every later rebuke has an addressable target. (Awaiting Jacob's explicit confirm.)
  • Commitment-detection is the core skill, register-sensitive. "Not copyright" and "ugh, no red-eyes" bind; "I'll just quit lol" doesn't. Under-extract from venting; when unsure, float. About half of real items arrive as casual asides — missing them is how trust dies.
  • Dialogue mechanics never become nodes (test: would the user later point at it?). Affect is not state. About a third of rounds correctly change nothing.
  • Flip-flops apply in utterance order, history kept. Refinement ≠ duplication: identity = role-in-structure, not wording.
  • Development rhythm (from the 22-round essay simulation): user plants a live root → agent inflates grey hypothesis → pushback converts grey to black or kills it. The map hardens exactly as fast as the user commits — never faster.
  • Most content never becomes items — drafts and process stay in the log. Items are the skeleton, not the flesh.

Worked material: docs/ontology/translation-essay.md (22-round map history, round anatomy, re-carve semantics) + the raw corpus.

§ 5Context composition: focus + lit

Replaces the earlier faders concept — killed 2026-08-12: "40% of context" is ill-defined; compression isn't a continuum and users can't perceive proportions.

Two separate needs, two simple mechanisms:

  • Inclusion (what the model can see) — a SET: each node is lit or dark. Binary.
  • Salience (what we're working on) — a POINTER: exactly one focus node per chat — the localization pointer the translation loop already maintains.

Detail level derives from role; the user never dials percentages:

FOCUS node      → full detail: whole item-tree, open questions, key verbatim
LIT nodes       → brief: one-paragraph summary each
ANCESTORS       → frame: one-liners (thesis, constraints never lost)
everything else → dark: absent
  • Seeds state the priority structure explicitly: "You are working ON [focus]. Background: [lit briefs]. Frame: [one-liners]." Lit nodes show token weights — the map doubles as a context-budget dashboard.
  • Mid-session, map changes ride in as labeled [map update] headers on the next user message — append-only, cache-friendly, marked as harness state, never as user words. Save points consolidate headers into a fresh seed.
  • The exact-rewind exception (Mark's ruling): within your own live chat, rewinding is a verbatim, instant, cache-friendly resume — a prefix is always self-consistent. Everything else re-seeds from the map. Two ops, one "go back" gesture.

§ 6Operations

Point and operate — speech is the API

"Drop objection 1 to argument 2" resolves via address + role-links to one item, applies the status change, then runs damage advice. Scoped mass-ops work ("park the whole Nara thing"), confirming when the resolved set looks bigger than intended. Homeless items resolve by type + topic + recency — how humans point in unstructured talk.

Delete → damage report → one confirm

Deleting or rejecting an item walks its links and sorts dependents: fatally hurt (advise delete) · degraded (advise review) · untouched (silent) — like a refactoring tool reporting broken call sites. Never auto-delete. MVP: downward only; upward (parent summaries) and sideways defer to v1.

Crystallization — dumb v0

No declared project? Items accumulate under the chat container. When enough cohere, the system offers: "want me to organize this?" One-word ratification re-homes them. Never forced — the honest floor is a structured-memory chat, which is already value.

Restructuring — manual in MVP

Drag items between containers; rename; create/cut containers. Two gestures the UI must never conflate: moving an item (re-home) vs re-linking it. Re-homing can stale content → mini rewrite flag. Re-carve automation deferred (spec preserved): map-level speech → gated reorganization, tombstones with forwarding aliases, ghost overlays for musing-register structure-talk.

Fold / merge — deferred, groundwork kept

The merge unit is a goal subtree; folding = distilling a completed structure into its parent's context. Under the item ontology, a fold is just a batch of contributions delivered at once — merge becomes a quantity, not a special thing.

§ 7UI

Two panes: map (left), workspace (right). The workspace shows either a chat or a node view (a container's items with statuses and provenance). The whole seam in one rule: click a node → see its contents; press Continue → a chat opens beneath it, seeded per §5.

  • Map v0 = plain interactive tree: indented, collapsible, status glyphs (✓ ○ ⚠ ✗ ⏸ ☐ ●), focus marker ▶, lit/dark state, token weights — the format validated in the simulation flipbook.
  • Async + pulse: chat never blocks on translation; the map catches up a beat behind; changed nodes pulse; clicking a pulsed node shows the round summary that caused the change. "What did you think I meant?" is always one click deep, and correcting the summary re-derives the alteration.
  • The galaxy (goals as stars, focus as your ship, lit = illuminated) is a future rendering of the same data — deterministic orbits, gravity as motion flavor only. Deferred to keep v0 honest; the renderer interface must not preclude it.

  • Wrap, don't rebuild (unchanged from v1): the SDK owns agent turns and resume.
  • Single user in MVP; the author field and immutable log future-proof multiplayer.
  • Translator outputs stored with provenance (prompt, model) — translations are auditable.

SDK integration contract (verified 2026-08-12)

  • Session birth — we compose. New chat = new SDK session with systemPrompt: {preset: 'claude_code', append: …} (keeps the full Claude Code harness: tools, MCP, subagents, permissions) + our composed seed as the opening message.
  • Mid-session — append, never rewrite. Our server constructs every user-message payload, so [map update] headers ride in as content blocks we prepend. The SDK transcript is strictly append-only — no API edits past messages — which matches rebuild-don't-splice exactly.
  • Exact rewind — the one constraint: resume + forkSession branch only from a session's latest state. Implementation: fork-at-save-point — fork the live session the moment a save point materializes (its latest state IS the save point); the fork's ID is the checkpoint handle. Between save points: prefix re-seed from our own log, clearly labeled approximate.
  • Custom tools: in-process MCP server registers harness functions (recall, later map-ops) as mcp__harnessmap__*.
  • Flagged risk: SDK auto-compaction has no documented disable flag; our short-chat design rarely triggers it, and a PreCompact hook archives if it does. Verify in the first spike.

§ 9MVP cut & roadmap

TD review outcomes (2026-08-12 — verdict: PROCEED WITH CHANGES, adopted): ① build order inverted — a headless translator eval is Phase A and the explicit kill-criterion, before any app code (implemented: src/eval/run.ts); ② the map store is event-sourced — append-only map_events is the source of truth, tables are a rebuildable projection (implemented); ③ rewind semantics specified: abandoned rounds' alterations demote to floated/provisional, never silently deleted; ④ v0 trimmed further — crystallization cut, damage triage reduced to inbound-link display, exact rewind gated on the SDK spike, click-ops before speech-ops; ⑤ SDK sessions demoted to best-effort cache (our log is canonical); ⑥ serial translation queue + "map is N rounds behind" indicator + backfill; ⑦ new open items: resolver evals, cost budgets, map digest for large projects, redaction escape hatch.

Success signal: users stop scrolling transcripts — they answer "where were we / what did we decide?" from the map, and drop/park/focus gestures become habitual. If the map isn't trusted as the record, nothing downstream matters.

v1 — "the harness for building"

Coding target: shadow-git workspaces (save point = commit, branch = git branch, jump = checkout). Re-carve automation. Upward damage. Galaxy-lite rendering. Recall tool. Translation-quality evals (commitment-detection precision/recall on seeded transcripts) — quality here is upstream of everything.

v2 — ambitions

Fold/merge of goal subtrees. Multiplayer maps. Agent-initiated cartography (the agent proposes forks, folds, cleanups). Map-level search. The map as a planning surface: sketch future containers as empty goals and let sessions grow toward them.
